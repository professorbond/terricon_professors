# CLAUDE.md — JanaМен (единое приложение)

Ты — Claude Code в репозитории **JanaМен** — HR-платформы для хакатона Jana Post × Terricon Valley (кейс Digital HR, 56 часов). Над репозиторием работают **два человека параллельно**: Даниил (этот Claude Code) и напарник. Задача Даниила:
1. **Сначала** собрать общий каркас приложения, на котором оба будут работать (этап 0).
2. **Потом** делать свои фичи (раздел 7), пока напарник делает обязательные экраны кейса на том же каркасе.

Прочитай этот файл целиком перед первой задачей. Если задача противоречит этому файлу — остановись и спроси Даниила.

> **Фактическое состояние (16.10.2026) — важнее разделов 3–4 ниже, где они расходятся:**
> - Основная ветка — **`feature`** (не `main`). Работа в ветках `dan/<feature>` → PR в `feature`.
> - **Фронтенд уже сделал напарник** в корне репо (`src/`, React 19 + TS 6 + Vite 8 + Tailwind 4 + React Router 7, без TanStack Query), со своей дизайн-системой JANA FLOW и правилами в `AGENTS.md`, `docs/DESIGN_SYSTEM.md`, `docs/SCREEN_MAP.md`. Фронтовую часть этапа 0 (§4.2: реестр, слоты, UI-кит) **не делаем** — работаем в его структуре; папку для экранов ext-фич согласовать с напарником.
> - **Бэкенд — Python/FastAPI** (согласовано; в README напарника упоминается ASP.NET — устарело). Живёт в `backend/`, `docker-compose.yml` в корне.
> - **Этап 0 (бэкенд) сделан**: `backend/app/core`, `integrations`, `modules/leave` (эталон типа заявки), seed, тесты. API — в формате контрактов фронта (`src/services/contracts.ts`): camelCase, роли `Employee|Manager|HRAdmin`, статусы `Submitted|Approved|Rejected|Escalated|Cancelled`, ошибки `{kind, code, message, fieldErrors, data}`. Описание — `docs/EXTENSION_POINTS.md`.
> - Отличия от §4.1: роли называются `Employee|Manager|HRAdmin`; фоновый тик — asyncio-цикл (без APScheduler); ставка `shift_rate` в seed — **за смену** (14 смен × 12 000 = 168 000 ₸ у Айгерим).

## 0. Контекст

**Jana Post** — логитех-компания: доставка из Китая (Pinduoduo, Taobao, 1688, Temu) в Казахстан и Центральную Азию, сортировочные центры в Алматы и Гуанчжоу, быстрый выход в новые страны, участник программы ЕБРР.

**Кейс:** единая HR-платформа: вход и 3 роли (сотрудник, руководитель, HR), профиль, заявка «Отпуск» или «Аванс» со статусом и историей, «Мои заявки», Jana Academy (курс, прогресс), AI Jana (ответы только по базе знаний, со ссылкой на источник, честное «нет ответа»), уведомления. Интеграции с 1С:ЗУП и Documentolog — mock, но место интеграции должно быть видно в архитектуре. Кадровые данные только читаются. Приветствуется RU/KZ.

**Наш инсайт:** Jana Post конкурирует за линейный персонал с Яндекс Про (деньги каждый день, график без начальника, всё видно в приложении). JanaМен даёт штатному сотруднику скорость и прозрачность гига плюс стабильность штата, а компании показывает, где она теряет людей.

## 2. Железные правила

1. **Одно приложение:** один бэкенд, один фронтенд, одна БД, одна авторизация, один интерфейс.
2. **Модули общаются через точки расширения каркаса** (реестры, события, слоты), а не через импорты внутренностей друг друга.
3. **Права проверяются на бэкенде** на каждом эндпоинте. Интерфейс только прячет кнопки.
4. **Время — только через `clock.now()`.** Никаких прямых вызовов текущего времени в бизнес-логике: демо «переводит время».
5. **Каждая фича Даниила выключается флагом** (`EXT_FEATURES`). Выключенная фича не регистрирует роуты, не появляется в меню и слотах.
6. **AI не принимает кадровых решений.** Решения принимают политики HR. AI отвечает по базе знаний и готовит черновики, которые утверждает человек.
7. **Данные «1С:ЗУП» (табель, оклад, грейд, остаток отпуска, дата пересмотра) только читаются** через `integrations/zup`. Изменения — документами через `integrations/documentolog`.
8. **Никаких реальных персональных данных, паролей и ключей** в репозитории. Ключи в `.env`, в репо — `.env.example`.
9. **Деньги — целые тенге (`int`).** Тексты интерфейса — только через i18n (`ru`, `kk`).
10. **Маленькие PR в `main`**, миграции не ломают друг друга (раздел 9).

## 4. Этап 0 — общий каркас (делает Даниил первым, ≈ 5 ч)

Цель: через 5 часов напарник клонирует `main` и сразу делает экраны, не думая про авторизацию, роли, БД и оболочку. **Как только каркас запускается — пуш в `main` и сообщение Даниилу «можно отдавать напарнику».**

### 4.1 Бэкенд

**Оргструктура (`core/org`):**
```
countries(code, name_ru, name_kk, timezone)                         # KZ, KG
units(id, country, kind[sorting_center|office|pickup], name, parent_id)
employees(id, full_name, login, password_hash, role[employee|manager|hr],
          country, unit_id, position, manager_id, hire_date, qualification, active)
```
- `rbac.py`: `require_role(...)`, `is_my_team(manager, employee)`, `can_view_employee(user, employee)` (сам, руководитель своей команды, HR).

**Mock 1С:ЗУП (`integrations/zup`), только чтение:**
```
zup_salaries(employee_id, monthly_base, shift_rate, night_bonus_rate)
zup_timesheets(employee_id, date, hours, shift_type)
zup_hr_attrs(employee_id, grade_code, last_salary_review_date, vacation_days_left, incidents_last_date)
zup_hire_offers(id, position, grade_code, country, offered_monthly_base, offered_at)
```
Интерфейс `ZupPort` с методами `get_salary`, `get_timesheet(period)`, `get_hr_attrs`, `list_recent_offers(since)` и реализация `MockZup`. В `docs/ARCHITECTURE.md` — где подключается настоящий 1С:ЗУП.

**Движок заявок (`core/requests`)** — общий для всех типов, на нём строят и напарник, и Даниил:
```
requests(id, type, employee_id, approver_id NULL, status[pending|approved|rejected|escalated|cancelled],
         payload jsonb, created_at, decided_at, decided_by NULL, decided_by_system bool,
         decision_reason_code NULL, decision_comment NULL)
request_events(id, request_id, at, actor_id NULL, actor_kind[user|system], event, data jsonb)
```
- **Реестр типов:** модуль регистрирует тип заявки: код, название (ключ i18n), схема `payload`, кто согласует (`approver_resolver`: руководитель / HR / никто), можно ли отзывать.
- **Хуки жизненного цикла** (через `core/events.py`): `request.created`, `request.before_decision` (обработчик может запретить решение, вернув ошибку), `request.decided`. Так гарантии Даниила навешиваются на «Отпуск» напарника **без правок его кода**.
- **API движка:** `GET /api/requests/my`, `GET /api/requests/{id}` (карточка + история), `GET /api/requests/inbox` (руководитель: своя команда; HR: адресованные HR), `POST /api/requests/{id}/decide {decision, reason_code?, comment?}`, `POST /api/requests/{id}/cancel`. Создание — через эндпоинт модуля типа (у каждого типа своя форма), который вызывает `requests.create(...)`.
- Системное решение: `requests.decide_by_system(request_id, decision, reason)` — для гарантий и «Зарплаты по факту».

**Уведомления (`core/notifications`):**
```
notifications(id, employee_id, kind, title_key, body_key, params jsonb, link, read, created_at)
```
`notify(employee_id, kind, title_key, body_key, params, link)`, `GET /api/notifications`, `POST /api/notifications/{id}/read`, счётчик непрочитанных. Подписка на `request.decided` — уведомление автору (по умолчанию).

**Прочее каркаса:**
- `integrations/documentolog`: `create_document(kind, employee_id, data) -> id` (mock, таблица `documents`).
- `integrations/bank`: `send_payout(employee_id, amount, reference) -> id` (mock, всегда успех).
- `integrations/llm`: `complete(system, messages) -> text`; без ключа — `None` (вызывающий использует экстрактивный режим).
- `clock.py`: `now()` = реальное время + смещение из `demo_state`.
- `core/demo`: `POST /api/demo/advance-time {hours}` (сдвиг + немедленный тик планировщика), `POST /api/demo/reset` (миграции с нуля + seed). Только при `DEMO_MODE=true`.
- `settings_api.py`: `GET /api/settings` → включённые фичи, страна и язык пользователя.
- `modules.py`: каждый модуль экспортирует `register(app, scheduler, events)`; `main.py` подключает модули из списка, ext-модули — только если флаг включён.
- Вход: `POST /api/auth/login {login, password}` → JWT `{sub, role, country, name}`; `GET /api/auth/me`.

### 4.2 Фронтенд

- **Оболочка:** шапка (логотип, язык RU/KZ, колокольчик с непрочитанными, пользователь), меню слева (на телефоне — нижняя панель), область контента. Адаптив обязателен.
- **Реестр модулей (`core/registry`):** модуль экспортирует объект:
  ```ts
  export const module: AppModule = {
    id: "ext-wage",
    feature: "wage_access",                   // флаг; нет флага — всегда включён
    routes: [{ path: "/wage", element: <WagePage/>, roles: ["employee","manager","hr"] }],
    menu: [{ to: "/wage", labelKey: "ext.wage.menu", icon: "wallet", roles: [...], order: 30 }],
    slots: { "home.widgets": [{ component: WageWidget, order: 10 }],
             "profile.sections": [...], "request.card.badges": [...], "request.decision.form": [...],
             "academy.course.badges": [...] },
    i18n: { ru, kk },
  };
  ```
  Все модули перечислены в одном файле `src/modules/index.ts` — **одна строка на модуль**.
- **Слоты** — места, куда модули вставляют свои блоки, не трогая чужие страницы:
  - `home.widgets` — главная (напарник рендерит `<Slot name="home.widgets"/>`);
  - `profile.sections` — профиль;
  - `request.card.badges` — карточка и строка заявки (бейдж срока);
  - `request.decision.form` — поля в окне решения по заявке (причина отказа);
  - `academy.course.badges` — бейдж «нужен для грейда».
- **UI-кит (`core/ui`)**: Button, Card, Badge, Modal, Table, Input, Select, Tabs, EmptyState, MoneyText (`84 000 ₸`), DateText. Цвета — CSS-переменные в `theme` (зелёный Jana Post).
- **Демо-панель** (только при `DEMO_MODE`): быстрый вход за персонажей seed, «+2 дня», «Сброс».

## 5. Что делает напарник (для понимания, не для тебя)

На каркасе он делает модули `profile`, `leave` (тип заявки «Отпуск» + форма), `academy`, экраны «Мои заявки», «Входящие» руководителя, центр уведомлений, главную страницу со слотом `home.widgets`. Заявку «Аванс» он **не делает**: её заменяет «Зарплата по факту» Даниила (сообщить напарнику).

Если Даниилу для фичи нужно что-то в модуле напарника — **не правь его код**, а попроси Даниила передать просьбу. Временно можно сделать заглушку внутри своего модуля с пометкой `TODO(partner)`.

## 6. Общие правила фич Даниила

- Таблицы с префиксом `ext_`.
- Каждый ext-модуль: `models.py`, `schemas.py`, `service.py`, `router.py`, `register.py`, `tests/`; на фронте — `index.ts` (AppModule), страницы, виджеты, `i18n/`.
- Связь с каркасом — через `core.requests`, `core.events`, `core.notifications`, `integrations.*`, `core.org`, `core.rbac`.
- Связь с модулями напарника — **только** через события, слоты и публичный API (`/api/...`). Например, курсы Academy читаем через его эндпоинт или через событие `academy.course_completed` (попросить напарника публиковать его; до этого — `TODO(partner)` + чтение напрямую из его таблицы в одном файле `integration.py`).
- Коды ошибок: `REASON_REQUIRED`, `COMMENT_REQUIRED`, `UNKNOWN_REASON`, `AMOUNT_EXCEEDS_AVAILABLE`, `LIMIT_PER_PERIOD`, `BELOW_MIN_AMOUNT`, `QUALIFICATION_MISMATCH`, `SHIFT_OVERLAP`, `FORBIDDEN`.

## 7. Фичи Даниила: спецификация

### 7.1 Гарантии и политики (`ext_guarantees`) — фундамент

**Данные:**
```
ext_policies(id, country, request_type, sla_hours, on_timeout[auto_approve|escalate_hr], enabled,
             wage_limit_pct, wage_max_per_period, wage_min_amount, review_period_months,
             replacement_cost_pct, avg_annual_salary, updated_by, updated_at)
ext_reasons(code, title_key, applies_to[])
ext_request_guarantees(request_id UNIQUE FK, policy_id, deadline_at, resolution[none|auto_approved|escalated], resolved_at)
```

**Правила:**
- Подписка на `request.created`: если для `(страна сотрудника, тип)` есть политика → создать `ext_request_guarantees` с `deadline_at = created_at + sla_hours`, событие в историю «Срок ответа до …», уведомление автору.
- Подписка на `request.before_decision`: при `rejected` без `reason_code` из справочника или без `comment` (≥ 10 символов) → запрет решения с `REASON_REQUIRED` / `COMMENT_REQUIRED` / `UNKNOWN_REASON`. Работает для **всех** типов заявок, включая «Отпуск» напарника.
- Тик: `pending` с истёкшим сроком → `auto_approve` → `requests.decide_by_system(approved)`; `escalate_hr` → статус `escalated`, адресат — HR, уведомления автору и HR. Событие в историю.
- Для денежных типов `auto_approve` запрещён валидацией политики.

**API:** `GET /api/ext/guarantees/summary/me`, `GET /api/ext/guarantees/reasons?type=`, `GET /api/ext/policies?country=` (hr), `PUT /api/ext/policies/{id}` (hr).

**Интерфейс:**
- Слот `request.card.badges`: «Ответ до 18 окт» / «Одобрено по сроку» / «Передано HR».
- Слот `request.decision.form`: при отказе — выбор причины + комментарий, кнопка неактивна, пока пусто.
- Слот `home.widgets`: блок **«Мои гарантии»** (доступно по факту; ответ по заявке до …; отказов без причины — 0; следующий пересмотр ЗП; смены).
- Страница HR «Политики»: таблица по стране и типу, редактирование.

**Готово, когда:**
- [ ] тест: отказ без причины / с неизвестной причиной → ошибка, статус не изменился;
- [ ] тест: после `advance-time` на sla+1ч заявка одобрена системой, есть событие и уведомление;
- [ ] тест: `auto_approve` для денежного типа не сохраняется;

### 7.2 Страны

- `country` есть у сотрудника, политик, грейдов, документов базы знаний.
- Новая страна = новые строки в seed/данных, без изменений кода.

### 7.3 «Зарплата по факту» (`ext_wage`) — гейм-чейнджер 1

**Тип заявки** `wage_access` (без согласующего). Данные: `ext_wage_withdrawals(id, employee_id, period, amount, request_id, document_id, payout_id, status, created_at)`.

**Расчёт (период — месяц по `clock.now()`):**
```
earned = sum(hours из табеля за период) * shift_rate (+ ночные по night_bonus_rate)
         # если shift_rate нет: monthly_base * отработано_смен / план_смен
withdrawn = sum(выводов за период со статусом paid|pending)
available = max(0, floor(earned * wage_limit_pct / 100) - withdrawn)
```
- Ограничения: `amount >= wage_min_amount`, `amount <= available`, выводов за период `< wage_max_per_period`.
- Вывод: `requests.create(type="wage_access")` → `decide_by_system(approved)` → документ «аванс по заявлению» в Documentolog (mock) → выплата через банк (mock) → уведомление «Деньги отправлены». Заявка видна в «Моих заявках» напарника автоматически.
- Расчётка человеческим языком: «смены + ночные − ИПН − ОПВ = итог» (ставки — из настроек страны, помечены как демонстрационные).

**API:** `GET /api/ext/wage/summary`, `POST /api/ext/wage/withdraw {amount}`, `GET /api/ext/wage/payslip-explained?period=`.

**Интерфейс:** страница `/wage` + виджет на главную. Крупно «Доступно сейчас: 84 000 ₸», ниже «Отработано 14 смен · заработано 168 000 ₸», кнопка «Получить», ввод суммы с подсказкой лимита, подтверждение, экран «Деньги отправлены»; вкладка «Почему столько».

**Готово, когда:**
- [ ] тест: сумма больше доступной → `AMOUNT_EXCEEDS_AVAILABLE` с `available`;
- [ ] тест: вывод сверх лимита за период → `LIMIT_PER_PERIOD`;
- [ ] тест: после вывода `available` уменьшился, есть заявка, документ, выплата, уведомление;
- [ ] 3 нажатия от главной.

### 7.4 «Открытая лестница» (`ext_ladder`) — гейм-чейнджер 2

**Данные:** `ext_grade_ladders(code, country, title_key, band_min, band_max, next_grade_code, required_course_ids[], min_months_in_grade, min_months_no_incidents)`, `ext_salary_reviews(id, employee_id, proposed_by, proposed_at, status, source_signal_id)`.

**Правила:**
- Текущий грейд и вилка, следующий грейд и вилка, критерии: курсы (из Academy напарника), месяцы в грейде, месяцы без замечаний (из mock 1С:ЗУП).
- Дата следующего пересмотра = последний пересмотр + `review_period_months` (или дата из `ext_salary_reviews`, если пересмотр предложен).
- Сотрудник видит **только** свой и следующий грейд; HR — все. Зарплаты конкретных людей не возвращаются никогда.

**API:** `GET /api/ext/ladder/me`, `GET /api/ext/ladder/course-tags` (для бейджа в Academy), `GET /api/ext/ladder/grades?country=` (hr).

**Интерфейс:** слот `profile.sections`: «Сейчас: Сортировщик · 230–270 тыс ₸» → «Дальше: Старший сортировщик · 270–320 тыс ₸», чек-лист критериев, «Осталось: 1 курс → +35 000 ₸ к нижней границе», кнопка «Перейти к курсу». Слот `academy.course.badges`: «Нужен для грейда SORT-2».

**Готово, когда:**
- [ ] тест: сотрудник не получает вилки других грейдов;
- [ ] тест: после завершения курса прогресс растёт;
- [ ] уведомление при выполнении критерия.

### 7.5 HR-пульт: радар удержания + счётчик (`ext_hr_console`)

**Данные:** `ext_risk_signals(id, employee_id, kind, details, detected_at, status[open|actioned|resolved], action, actioned_at, retained_confirmed)`.

**Сигналы (пересчёт тиком и кнопкой):**

| kind | Условие |
|---|---|
| `no_review` | с последнего пересмотра ≥ `review_period_months` |
| `rejections` | ≥ 2 отклонённых заявок за 180 дней |
| `pay_equity` | недавний оффер на тот же грейд и страну выше оклада сотрудника |
| `slow_answers` | ≥ 2 заявок за 90 дней решены позже срока или системой |
| `open_grievance` | обращение без решения дольше срока |

**Запрещено** использовать выводы «Зарплаты по факту», вопросы к AI, время прихода и любые поведенческие данные (тест: модуль не импортирует эти модели).

**Действия HR:** «Предложить пересмотр» → `ext_salary_reviews`, уведомление сотруднику, сигнал `actioned`. «Сотрудник остался» → `retained_confirmed=true`.

**Счётчик:** `saved = count(retained_confirmed) * avg_annual_salary * replacement_cost_pct / 100`.

**API (hr):** `GET /api/ext/hr/risks?country=`, `POST /api/ext/hr/risks/{id}/propose-review`, `POST /api/ext/hr/risks/{id}/confirm-retained`, `GET /api/ext/hr/savings`.

**Интерфейс:** страница «HR-пульт», вкладка «Радар». Крупно «Радар сохранил 12 сотрудников = 10,8 млн ₸», карточки риска с причинами человеческим языком и кнопкой действия.

**Готово, когда:**
- [ ] на seed минимум 3 сотрудника в зоне риска с разными причинами;
- [ ] тест: `employee` и `manager` → 403;
- [ ] тест: модуль не читает `ext_wage_withdrawals` и вопросы к AI;
- [ ] после «предложить пересмотр» уведомление у сотрудника и новая дата в лестнице.

### 7.6 «Обращение» (`ext_grievance`) — под стандарты ЕБРР

- Тип заявки `grievance`, согласующий — HR (не руководитель), гарантия срока по политике.
- `payload`: категория, текст, `anonymous`.
- Анонимное: автор не возвращается никому, кроме самого автора. Руководитель не видит обращений вообще.
- Обращение без решения дольше срока → сигнал `open_grievance`.
- В README честно: в прототипе автор хранится в БД, чтобы видеть ответ.

**Готово, когда:**
- [ ] тест: HR получает анонимное обращение без автора;
- [ ] тест: руководитель → 403 на обращения.

### 7.7 AI Jana (`ai_jana`) — если делает Даниил

**Поиск:** документы `seed/kb/<country>/*.md` → таблица `kb_docs(id, country, title, source_label, body_md, status[published|draft])` → чанки по заголовкам (≈ 500–800 символов) → BM25 **только по стране пользователя**. Порог `KB_MIN_SCORE` (по умолчанию 0.35, подобрать на наборе вопросов): ниже — «Надёжной информации нет» + кнопка «Спросить HR» (создаёт обращение).

**Защита (до поиска):**
- Вопросы о данных **других** людей (зарплата, больничный, оценка коллеги/начальника) → отказ без поиска. Правила + опционально LLM-классификатор; тесты на 10+ формулировок.
- Вопросы о **своих** данных («сколько у меня отпуска», «сколько могу снять») → ответ из 1С:ЗУП / «Зарплаты по факту» только для текущего пользователя, источник «Данные 1С:ЗУП».

**Ответ:** с LLM — только по переданным фрагментам, коротко, на языке вопроса, со ссылками `[Документ, раздел]`; маркер `NO_ANSWER` → честный отказ. Без ключа — лучший фрагмент + источник. Ответ без источников не отдаётся. Имя модели Anthropic проверить в документации.

**Логирование:** `kb_questions(id, country, question, answered, top_score, gap_group_id, asked_at)` — **без** идентификатора сотрудника.

**Seed базы:** `kz` и `kg` — отпуск, переработки, «Зарплата по факту», гарантии и сроки, обращения, грейды и пересмотр (пометка «демо-выдержка»), цифры различаются. Оплату ночных смен в KZ **не** описывать — для демо пробелов.

**API:** `POST /api/ai/ask {question, lang}` → `{answer, sources[], answered, escalate_available}`.

**Готово, когда:**
- [ ] «Какая зарплата у моего начальника?» → отказ без поиска;
- [ ] KZ и KG получают разные источники;
- [ ] вопрос вне базы → отказ + запись вопроса;
- [ ] ответ без источников невозможен.

### 7.8 Биржа смен, мини (`ext_shifts`) — только если персонал сменный

**Данные:** `ext_shifts(id, unit_id, date, start_time, end_time, qualification, assignee_id NULL, status[assigned|offered|open|taken], pay_preview, published_by)`, `ext_shift_events`.

**Правила:** «Отдать смену» — коллега того же центра и квалификации без пересечения берёт, оба получают уведомления, руководитель видит, но не согласует. «Открытая смена» — руководитель/HR публикует с `pay_preview`, сотрудник берёт в одно нажатие. Нельзя взять смену в прошлом или пересекающуюся.

**API:** `GET /api/ext/shifts/my`, `GET /api/ext/shifts/available`, `POST /api/ext/shifts/{id}/offer`, `POST /api/ext/shifts/{id}/take`, `POST /api/ext/shifts` (manager/hr).

**Готово, когда:** тесты на квалификацию и пересечение; взять смену — 1 нажатие, видно «+12 000 ₸».

### 7.9 Рентген руководителей (вкладка HR-пульта)

- Метрики за 90 дней по заявкам и гарантиям: медианное время ответа, доля отказов, решения позже срока, люди команды в зоне риска.
- HR видит всех; руководитель — только себя и перцентиль; сотрудник — 403.
- Подача: «Аналитика HR-процессов», не оценка эффективности людей.

**API:** `GET /api/ext/hr/xray` (hr), `GET /api/ext/hr/xray/me` (manager).

### 7.10 Пробелы базы знаний (`ext_kb_gaps`)

- Вопросы с `answered=false` группируются: нормализация (lowercase, `pymorphy3`, стоп-слова) + TF-IDF + косинус ≥ 0.5; метка — топ-слова или формулировка от LLM.
- HR видит «23 вопроса: оплата ночных смен (KZ)» без имён.
- «Подготовить ответ» → LLM пишет черновик правила по шаблону (без LLM — пустой шаблон). HR правит и публикует → документ в базе, переиндексация. AI ничего не публикует сам.
- Если AI Jana делает напарник — его AI при отказе публикует событие `ai.unanswered {question, country}`, модуль подписывается на него.

**API (hr):** `GET /api/ext/kb/gaps?country=`, `POST /api/ext/kb/gaps/{id}/draft`, `PUT /api/ext/kb/docs/{id}`, `POST /api/ext/kb/docs/{id}/publish`.

**Готово, когда:** после публикации тот же вопрос получает ответ с источником «Внутреннее правило»; в API нет идентификаторов сотрудников.

## 9. Git и миграции (чтобы параллельная работа не ломалась)

- `main` всегда запускается. Работа — в ветках `dan/<feature>` и `<напарник>/<feature>`, короткие PR, мердж несколько раз в день.

- **Общие файлы** (`src/modules/index.ts`, список модулей бэкенда, `ru.json`/`kk.json` каркаса) — только добавление строк; свои ключи i18n — в словаре модуля, не в общем файле.
